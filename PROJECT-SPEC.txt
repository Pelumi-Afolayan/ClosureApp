2. THE USER'S ORIGINAL IDEA AND CONFIRMED REQUIREMENTS

The user wants to build a closure web app that can be installed as a PWA and used on a phone. They confirmed that its focus is breakups.

The user's requested features are:
- Each person must have an account.
- Offer options for what they want to achieve.
- Users must be able to select multiple goals, including every goal.
- A daily streak counter.
- Words of encouragement every day.
- A place to describe what the other person did that hurt them.
- A place to write whatever they want.
- A way to record how they feel.

The user specifically corrected the goal selection: it must NOT be a single-choice field. They can choose all options.

Working name: Closure. No logo, final brand identity, domain, or tagline has been approved.

3. PRODUCT PURPOSE AND TONE

The proposed purpose is a private space for people processing a breakup: express what hurt, reflect on feelings, and build a daily check-in habit at their own pace.

Use warm, natural, supportive language. Avoid shaming someone for missing days or having difficult feelings. Do not promise that an app will heal a breakup or measure whether someone has fully recovered. Progress should describe activity and mood history rather than a percentage healed.

Two possible product directions were raised: a gentle journal or a structured programme with daily activities. The user has not chosen between them. The current first-release plan focuses on journaling and check-ins. A structured programme is not an approved requirement.

4. ONBOARDING AND GOALS

Proposed onboarding fields:
- Preferred name.
- Goals, with multiple selection.
- Optional breakup date.
- Current feelings.

The original suggested goals were:
1) Move on.
2) Find peace.
3) Rebuild confidence.
4) Accept the breakup.
5) Reduce/break the urge to reach out.

The later project plan suggested two additional options:
6) Stop blaming myself.
7) Understand my feelings.

These last two are planning suggestions, not individually requested by the user. Keep the selection flexible and allow goals to be changed in Settings. Selected goals should guide encouragement and prompts. Do not require the user to prioritise only one goal.

Sensitive story questions should be optional and revisitable, so someone can start using the app without immediately telling their entire story.

6. DAILY CHECK-IN AND STREAK RULES

The assistant proposed that the main streak should count consecutive days with a saved mood check-in. The user requested a daily streak but has not explicitly selected its precise counting rule; check-ins are the current working proposal.

Proposed behaviour:
- A saved mood check-in earns that day's credit.
- Writing a note is optional.
- A difficult mood still earns credit.
- Multiple check-ins or edits on the same day do not add extra streak days.
- Missing a day breaks the consecutive streak; history and longest streak remain.
- Encourage returning without guilt.

Implementation details to settle when building:
- Use a defined user timezone to identify the local check-in date.
- Prefer one record per user per local date; editing updates that record.
- Test midnight boundaries, duplicate submissions, missed days, and timezone behaviour.
- If today has no check-in yet but yesterday does, the streak should remain visible until the user has actually missed the current day.

Possible mood options discussed: sad, angry, relieved, hopeful, numb. Multiple feelings were proposed in the plan. Final labels and any intensity scale have not been chosen.

An optional no-contact counter was suggested for later. It must remain separate from the main daily check-in streak and is not part of the agreed core brief.

7. DAILY ENCOURAGEMENT AND PROMPTS

The first version should use a curated collection of messages and journal prompts organised by goals. No AI integration has been agreed.

Proposed behaviour:
- Select encouragement relevant to the user's chosen goals.
- Keep the same message throughout a given local day.
- Change it on a new day.
- Avoid unnecessary repeats when practical.
- Provide prompts while preserving the option to write freely.

No encouragement dataset has been created yet. Content quantity, final copy, and selection algorithm are still to be implemented. Do not assume an external quote API is necessary.

8. TECHNOLOGY AND STYLING DIRECTION

The current proposed stack is:
- React with JavaScript, using Vite.
- Tailwind CSS v4.
- React Router for screens and routing.
- Supabase for authentication and database storage.
- Lucide icons.
- PWA configuration, implementation approach still to be selected.

The user agreed to the Tailwind styling recommendation and then asked for the project structure. JavaScript is the current plan; do not switch to TypeScript without discussing it.

Visual direction proposed:
- Warm cream background.
- Muted sage green for main actions and selected options.
- Dark charcoal text.
- Rounded cards.
- Subtle shadows.
- Generous spacing.
- Gentle transitions with attention to reduced-motion preferences.

Exact colour values, typography, logo, dark mode, illustrations, and final layouts have not been chosen or built.

Create reusable Button, Input, Card, and Modal components to avoid repeating styling. Keep a small global CSS file for the Tailwind import, shared theme values, fonts, and animations.

10. DATABASE PROPOSAL — NO SQL HAS BEEN WRITTEN

Supabase Auth handles accounts separately from these application tables:

profiles:
- User identity linked to the authenticated account.
- Preferred name.
- Selected goals (multiple).
- Timezone.
- Optional breakup date.
- Onboarding completion state.

check_ins:
- Owner/user ID.
- Local check-in date.
- Selected moods.
- Optional note.
- Creation/update timestamps.
- Suggested uniqueness: one record per user and local date.

stories:
- Owner/user ID.
- Saved responses to story prompts.
- Creation/update timestamps.
- Exact response representation is undecided.

journal_entries:
- Owner/user ID.
- Entry content, optional title, timestamps.
- Entry type distinguishing ordinary writing and unsent letters.
- Optional prompt reference if needed.

The full schema, field types, indexes, migrations, triggers, and row-level security policies still need to be designed.

Every personal table must enforce ownership in the database, not merely hide records in React. Verify that one authenticated account cannot read or change another account's data. Browser environment variables must never contain privileged server credentials. Account deletion needs an appropriate authenticated server-side implementation; do not put admin deletion credentials in the frontend.
